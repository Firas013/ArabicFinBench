# Adding a document to the benchmark

What you have to produce for a new PDF, and what the harness does with it.

You author **one file**: the ground truth. Everything else is generated.

---

## 1. Files

```
test_2/
  Test_2.pdf          ← the source document.  YOU SUPPLY.  never committed
  Test_2.json         ← the ground truth.     YOU AUTHOR.  the only hand-written file
  Test_2.md           ← generated by afb_gt_to_sidecar.py
  Test_2.test.json    ← generated by afb_gt_to_sidecar.py
```

The directory name is free; the **stem must match the PDF** (`Test_2.pdf` →
`Test_2.json` → `Test_2.md`), because the harness discovers a test case by
looking for `<pdf_stem>.test.json` beside the PDF.

Add the directory to `.gitignore`. Source filings are never committed — the
pre-commit hook and CI both refuse them (`gt/CONVENTIONS.md` §6).

---

## 2. The ground truth file

Exactly two keys. Nothing else is read.

```json
{
  "lines": [
    { "text": "قائمة المركز المالي" },
    { "text": "كما في ٣١ ديسمبر ٢٠٢٤ م" }
  ],
  "tables": [
    {
      "rows": [
        ["٣١ ديسمبر ٢٠٢٣ م", "٣١ ديسمبر ٢٠٢٤ م", "إيضاح", "الموجودات"],
        ["",                  "",                  "",      "الموجودات المتداولة"],
        ["٨٣٩,٨٢١",           "٨٦٦,٠٨٣",           "",      "نقد وأرصدة لدى البنوك"],
        ["٣,٧٨٠,٢٠٠",         "٢,٧٩٠,٣٩٤",         "٥",     "ذمم مدينة تجارية ، بالصافي"]
      ]
    }
  ]
}
```

- **`lines`** — every non-table printed line, in reading order, across all
  pages. Headers, titles, footers, note paragraphs, page numbers.
- **`tables`** — one entry per table on the page, in document order. `rows` is
  a rectangular matrix of strings. Pad short rows with `""`.

UTF-8, no BOM. Do not escape the Arabic.

---

## 3. The five rules that decide whether the file is usable

Full reasoning in [gt/CONVENTIONS.md](../arabicfinbench/gt/CONVENTIONS.md).
These are the ones that will actually bite you.

### 3.1 Column order — pick one direction and hold it

**The single most important rule.** Arabic statements read right-to-left, so
the row label is normally the *rightmost* column and therefore the **last**
element of the array. Comparative years run to its left.

Whatever you choose, **use it for every table in the document**. Canon can fold
digits and section rows; it cannot repair a ground truth that contradicts
itself, because a reversed row is still a valid row.

> This is not hypothetical. In `Test_1`, table 0 is label-last while tables 2–4
> are the reverse. Against an identical parse, positional cell agreement was 98%
> for the first and 0–33% for the others.

### 3.2 Transcribe verbatim — do not normalise while annotating

Keep Arabic-Indic digits (`٨٣٩,٨٢١`) if the page uses them. Keep the spacing,
the separators, the `،`, the parentheses on negatives. Canon folds all of this
at scoring time, applied to both sides. Normalising by hand is silent,
inconsistent between annotators, and destroys the record of what the page said.

### 3.3 Section headers — encode them, sparsely

A section header gets its own row, label in the label column, every other cell
empty:

```json
["", "", "", "الموجودات المتداولة"]
```

Do not merge it into the header row. Canon lifts these out before the table
metrics run, so a system that emits the same header as a full-width `colspan`
scores identically.

⚠️ Any row with **exactly one non-empty cell** is treated as a section header.
So **give totals a label** — a bare total with no label is indistinguishable
from a section and will be lifted out of the grid.

### 3.4 Blank rows — do not encode them

A row with no content in any cell is not part of the table.

### 3.5 An empty cell is not a zero

Leave it `""`. Never write `"0"` for a blank. The null-correctness metric exists
precisely to catch a system that does this, and a ground truth that does it
first makes the metric blind.

The conventional dash `-` (nil, printed) is fine and is treated as null.

## 4. Generate, run, score

```bash
# 1. GT -> harness sidecar + expected_markdown
python scripts/afb_gt_to_sidecar.py test_2/Test_2.json test_2/Test_2.pdf

# 2. run whatever systems you want
extract-bench run llamaparse_agentic --input_dir test_2
python scripts/afb_run_openrouter.py --input-dir test_2      # the VLMs

# 3. score once into the store, then read it as often as you like
python scripts/afb_results.py --record --pipeline llamaparse_agentic --input-dir test_2
python scripts/afb_results.py
```

`afb_results.py` currently pins `DOCUMENT = "test_1/Test_1"`; point it at the
new id to render that document's table.

## 5. Before you trust the numbers: check the ground truth

The GT is scored against, so a defect in it becomes every system's error.

```python
from arabicfinbench.gt.integrity import validate_gt_schema, admit_page, check_relations

validate_gt_schema(payload, source="test_2/Test_2")   # shape
admit_page(payload, relations, source="test_2/Test_2")  # arithmetic must reconcile
```

`admit_page` raises `AdmissionError` if any declared relation fails to
reconcile exactly. **A page whose own totals do not add up is rejected**, not
scored — an unreconciled ground truth silently penalises every system.

Declare the relations you can check: block sums, roll-forwards, note-to-line
agreements. Exact `Fraction` arithmetic, no float tolerance.

## 6. Optional: the F axis

To score arithmetic consistency rather than only checking your own GT, add
`math` rules to the sidecar:

```json
{
  "test_rules": [
    {
      "type": "math",
      "id": "current_assets_block",
      "math_type": "block_sum",
      "total": "t0.r7.c1",
      "addends": ["t0.r2.c1", "t0.r3.c1", "t0.r4.c1", "t0.r5.c1", "t0.r6.c1"],
      "period": "2024",
      "scope": "balance_sheet",
      "unit": "SAR",
      "tolerance": "0.5"
    }
  ]
}
```

`math_type` is one of `block_sum`, `roll_forward`, `cross_statement`,
`note_to_line`, `tolerance_band`. `tolerance` is **per addend** and is scaled by
their count at evaluation time. Use `tolerance_band` with `base` and `rate` where
the page prints a rounded rate.

Without these, the F column reports nothing — which is honest, not a gap in the
code.

## 7. What makes a document worth adding

The current corpus saturates: seven of twelve systems land inside a 0.127 TRM
band on `Test_1`, which is inside the noise for a single document. A new file
adds most when it is *harder in a specific way*:

- a lower-quality or skewed scan
- stamps, signatures or handwriting over figures
- merged cells, or headers spanning two levels
- a different auditor's layout conventions
- more pages, or a statement type not yet covered

A second clean, well-typeset filing will mostly reproduce the existing
clustering. The bottleneck is document difficulty and count, not metrics.
